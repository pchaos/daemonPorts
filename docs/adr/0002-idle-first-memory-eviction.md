# Idle-first memory eviction under dual-memory-critical condition

Status: accepted

When physical and virtual (swap) memory both stay above their configured critical thresholds continuously (default 15 minutes), gatekeeper automatically stops the managed child config item whose port has been free of data traffic the longest. The victim is selected by longest idle time (now − `lastActiveTime_`, the same signal the existing `idle_minutes` auto-stop uses), tie-broken toward higher RSS; if every running child has recent traffic, the least-recently-active one is still evicted. Stopped entries are sticky-disabled for the rest of the run so `auto_restart` cannot resurrect them, and unlike the reversible `idle_minutes` auto-stop, eviction only re-arms on daemon restart or `/reload`. We chose availability-first eviction (idle before heavy) over heaviest-first: killing the biggest memory consumer frees more per kill but disruptes an in-use service, whereas evicting the idle service minimizes service loss at the cost of gradual, minutes-scale relief — and the alternative to any controlled eviction is the kernel OOM killer, which can kill gatekeeper or an active backend without a sticky disable.
